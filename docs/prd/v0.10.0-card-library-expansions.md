# PRD — v0.10.0 Card Library & Expansion System (+ four bug fixes)

Status: ready-for-agent · Target release: v0.10.0 (Android) · Author: agent (from owner stories, 2026-06-23)

## Problem Statement

As a homebrew Daggerheart player, RuneKeep only lets me *consume* the built-in card catalog. The
"Cards" destination on the main menu is a read-only archive — I can't author my own cards there,
I can't bundle a set of homebrew cards into something I can hand to a friend, and there is no way to
receive someone else's homebrew and have it show up during character creation. Custom cards today
only exist *inside a single character sheet* (`inventoryCustom`, `customCards` on the `CharacterFile`);
they can never become reusable content. There is also no concept of an **expansion** — a versioned,
shareable bundle of homebrew (new ancestries, communities, domains, subclasses, even whole classes)
that updates in place when its author ships a new version.

Separately, four concrete bugs hurt real play:

1. **Inventory custom-card creation is a dead end.** In character creation's inventory step, the
   "Create item" button re-opens the editor on the same single card forever; a created custom card is
   never selectable, and the counter never advances, so it feels permanently stuck in "creating."
2. **Level-up trait upgrades are broken.** The same trait can be upgraded twice in one level, and the
   "already upgraded" marks never reset when you cross into a new tier (they only clear at level 5 and
   8, never at level 2). By level 9 every trait is marked, so the trait advancement can never be
   completed and **leveling past ~level 8 becomes impossible**.
3. **Domain cards stop being added at level 3+.** Domain cards chosen during level-up stop appearing
   in the carousel from level 3 onward. The 5-active-domain-card cap is leaking into what the UI
   treats as "owned," dropping newly chosen cards from the visible deck.
4. **The card archive hides all weapons and armor.** The archive ("Card archive" / gallery) only
   shows catalog cards (domain/ancestry/community/subclass). Weapons and armor (tiers 1–4) never
   appear, even though they have a perfectly good code renderer already.

## Solution

Introduce a first-class, app-level **Card Library** reachable from the main menu's "Cards"
destination, and an **expansion** content unit that can be authored, shared, versioned, and enabled
per character-creation session.

- **Library vs. sheet cards.** Make the distinction explicit. *Sheet cards* are the cards on one
  character. *Library cards* are reusable homebrew content, organised into **expansions**, that live
  in their own app-level store (independent of any character) and feed character creation.
- **Authoring.** A full creation UI in the library lets the player make custom cards and configure
  each as an **ancestry** (with mixed-ancestry line support), **community**, **domain card** (with a
  domain + level), **subclass** (single card), or a **multi-page class** (the Druid/Ranger/Seraph
  shape). New domains and new classes are first-class: a custom class can declare its two domains.
- **`.rkp` file format.** Everything the app exports/imports uses a single envelope format with the
  `.rkp` extension (an unoccupied extension; the only prior art is an Age of Empires keybind/profile,
  no real-world conflict). An `.rkp` can carry a **character**, a **single card**, or an **expansion**
  (a bundle of cards). It is versioned JSON.
- **Sharing.** Primary path: export/import `.rkp` files via the OS share sheet
  (`expo-sharing` + `expo-document-picker`, already installed, works in Expo Go and the APK).
  **NFC tap-to-share** between two Android devices is an APK-only enhancement layered on top (see
  Out of Scope / Further Notes for the SDK-54 constraint). Expansions carry a **version**; importing
  an expansion you already have **updates it in place** instead of duplicating it.
- **Expansion-gated character creation.** If the player has ≥1 expansion installed, character
  creation opens with an **expansion picker**: choose which expansions are enabled for this session
  (with quick details per expansion), select/deselect freely. Enabled custom content then appears in
  the relevant creation steps (custom ancestries, communities, domains, subclasses, classes), with
  mixed-ancestry cross-out support intact for custom ancestries.
- **Single cards into a character sheet, not the library at large.** A *single* `.rkp` card can be
  imported directly onto a character sheet (its card carousel). Adding content to the *library* is
  done by authoring there or importing an *expansion*. (Owner clarification: single cards are
  additive to a sheet; the library is organised by expansions.)

Plus the four bug fixes, each a small, well-scoped change to existing modules.

## User Stories

### Library — navigation & model
1. As a player, I want the main menu's "Cards" destination to open a **Card Library**, so that I have a home for all reusable homebrew content, separate from any character.
2. As a player, I want the library to clearly separate **system content** (the built-in catalog) from **my homebrew expansions**, so that I always know what's official vs. custom.
3. As a player, I want my homebrew organised into **expansions** (named bundles), so that related cards travel together.
4. As a player, I want to still **browse the full system archive** (all catalog cards) from the library, so that I keep the existing read-only browsing.
5. As a player, I want the library to persist across app restarts independently of any character, so that my homebrew isn't tied to a single character file.

### Library — authoring cards
6. As a homebrew author, I want to **create a new expansion** (give it a name, description, author, version), so that I can group my cards.
7. As an author, I want to **add a card to an expansion** and choose its **content type**: ancestry, community, domain card, subclass, class, or generic, so that the card behaves correctly in character creation.
8. As an author, I want to **edit** any card in my expansion (title, art, body text, color, structured effects/modifiers, type label), so that I can refine homebrew over time.
9. As an author, I want to **delete** a card from my expansion, with a confirm safeguard, so that I don't lose work by accident.
10. As an author creating a **domain card**, I want to assign it a **domain** (existing or a new custom domain) and a **level (1–10)**, so that it slots into the right domain pool at the right level during creation and level-up.
11. As an author, I want to **create a new domain** (name, identity color), so that my domain cards can belong to a homebrew domain.
12. As an author creating a **subclass**, I want to assign it to a **class** (existing or custom) and author a single subclass card, so that it appears when that class is chosen.
13. As an author creating a **class**, I want to author a **multi-page class** like the built-in ones (name, starting evasion/HP, class items, hope feature, feature pages, and its two domains), so that my class is fully playable in creation.
14. As an author creating an **ancestry**, I want to mark which trait line carries the ancestry's passive effect (line 1 or line 2), so that mixed-ancestry cross-out disables the correct half.
15. As an author of a mixed-ancestry-capable ancestry, I want to define **where the two feature lines sit on the card** (the cross-out strike regions), so that mixing it with another ancestry crosses out the right lines flawlessly.
16. As an author, I want a **live preview** of the card in its real rendered form while editing, so that I see exactly what players will get.

### `.rkp` format & sharing
17. As a player, I want a single **`.rkp`** file format for everything I export or import (characters, single cards, expansions), so that there's one consistent, recognisable file type.
18. As a player, I want to **export a character** as `.rkp`, so that I can back it up or share it.
19. As a player, I want to **import a character** from `.rkp`, so that I can restore or receive one.
20. As an author, I want to **export an expansion** as `.rkp`, so that I can share my whole homebrew set in one file.
21. As a player, I want to **import an expansion** `.rkp`, so that I can use a friend's homebrew.
22. As an author, I want to **export a single card** as `.rkp`, so that I can share just one card.
23. As a player, I want to **import a single card** `.rkp` **onto a character sheet** (its carousel), so that I can use a one-off card without managing an expansion.
24. As a player importing content, I want the app to **detect the `.rkp` payload type** (character / card / expansion) and route it correctly, so that I don't have to pick the right import button.
25. As a player, I want `.rkp` import to **validate** the file and reject corrupt or incompatible files with a clear message, so that a bad file can't crash or corrupt my data.

### Expansion versioning
26. As an author, I want each expansion to carry a **version** (and an identity that survives renames), so that updates can be recognised as the same expansion.
27. As a player importing an expansion I **already have**, I want the app to **update it in place** (apply the new version) rather than create a duplicate, so that my library stays clean.
28. As a player, when an incoming expansion is the **same or older** version than mine, I want to be told and allowed to skip or overwrite, so that I don't silently downgrade.
29. As a player, I want updating an expansion to **preserve characters already built** with its content as much as possible (content referenced by id keeps resolving), so that updates don't break existing characters.
30. As a player, I want to see an expansion's **name, author, version, card count, and description** (quick details) before enabling or importing it, so that I know what I'm getting.

### NFC tap-to-share (Android, APK-only)
31. As an Android player, I want a **"Send via NFC"** option for a single card or an expansion, so that I can hand homebrew to a friend by touching phones.
32. As an Android player, I want a **receive** path so that when a sender taps, my device ingests the incoming card/expansion through the same import + versioning pipeline as `.rkp` files.
33. As a player on a build without NFC (Expo Go or iOS), I want the NFC option to be **absent or clearly disabled**, with `.rkp` file sharing always available, so that sharing always works somehow.

### Expansion-gated character creation
34. As a player starting character creation **with ≥1 expansion installed**, I want an **expansion picker** first, so that I choose which homebrew is in play for this character.
35. As a player, I want to **select/deselect** each expansion in the picker, so that I control the content pool.
36. As a player, I want **quick details** for each expansion in the picker (name, author, version, what content types it adds), so that I can decide.
37. As a player with **no expansions**, I want creation to proceed exactly as today (no extra step), so that the base experience is unchanged.
38. As a player, I want enabled expansions' **custom ancestries** to appear in the ancestry step, including mixed-ancestry support, so that homebrew ancestries are first-class.
39. As a player, I want enabled expansions' **custom communities** to appear in the community step.
40. As a player, I want enabled expansions' **custom domain cards** to appear in the domain step for the matching domain/level (including domains introduced by a custom class).
41. As a player, I want enabled expansions' **custom subclasses** to appear in the subclass step for the matching class.
42. As a player, I want enabled expansions' **custom classes** to appear in the class step, fully playable (multi-page feature cards, two domains, starting stats), so that I can build a homebrew-class character.
43. As a player, I want a created character to **record which expansions/content it used**, so that opening that sheet later still resolves its custom cards.

### Bug 1 — inventory custom-card "Create item" should add a selectable card
44. As a player in the inventory step, I want the last card in the carousel to be a **"Create card" button-card** (like the Mixed Ancestry toggle card), so that creating is an obvious, repeatable action.
45. As a player, when I activate "Create card", I want a **new card added to the left of the button** that I then edit, so that each creation produces its own distinct card.
46. As a player, after saving a created card, I want it to be a **normal selectable carousel card** (toggle to include/exclude), not a perpetual edit target, so that I can actually choose it.
47. As a player, I want to create **multiple** custom inventory cards this way, each independently selectable, so that I can add several homebrew items.
48. As a player, I want the "Create card" button to always say **"Create"** (it never doubles as edit/select), so that its role is unambiguous; editing a created card is a separate affordance.

### Bug 2 — level-up trait upgrades
49. As a player upgrading traits at level-up, I want to be **unable to pick the same trait twice in one level**, so that I can't double-upgrade one trait.
50. As a player, I want a trait I've upgraded to be **marked for the rest of the tier**, so that I can't re-upgrade it until the next tier.
51. As a player crossing into a **new tier (levels 2, 5, 8)**, I want my trait-upgrade marks to **reset**, so that I can upgrade traits again in the new tier.
52. As a player, I want to be able to **complete the trait advancement at every level including 9 and 10**, so that leveling is never soft-locked.
53. As a player, I want to still be able to upgrade **two distinct traits per applicable level-up**, so that the advancement budget is unchanged.

### Bug 3 — domain cards always added on level-up
54. As a player choosing a domain card at level-up, I want it **always added to my owned cards / carousel**, at **every level including 3+**, so that my chosen cards never vanish.
55. As a player, I want the **5-card cap to apply only to which domain cards are *active/equipped***, never to whether a chosen card is owned/visible, so that I keep everything I picked.
56. As a player with more than 5 owned domain cards, I want to **manage which 5 are active** (existing behaviour), while all owned cards remain in the deck.

### Bug 4 — weapons & armor in the archive
57. As a player browsing the card archive, I want to see **all weapons** (primary and secondary) across **tiers 1–4**, so that I can study every weapon.
58. As a player, I want to see **all armor** across **tiers 1–4** in the archive.
59. As a player, I want weapons/armor in the archive rendered as their proper **forged cards** (the existing code renderer), so that they look like real cards without needing image assets.
60. As a player, I want to **filter the archive by weapon/armor and by tier (1–4)**, so that I can find equipment quickly alongside the existing kind/domain/level filters.

## Implementation Decisions

### Modules to build/modify

**New deep modules (pure, testable in isolation):**

- **`rkp` (file envelope)** — `src/lib/rkp.ts`. Encodes/decodes the `.rkp` envelope:
  `{ format: 'rkp', rkpVersion: number, kind: 'character' | 'card' | 'expansion', payload }`.
  Pure functions `serializeRkp(kind, payload)`, `parseRkp(text) -> { kind, payload }` with validation
  (throws/returns a typed error on bad input). Reuses the existing `CharacterFile`
  serialize/validate for the `character` kind. No filesystem here — that lives in the store.
- **`expansion` (model + version logic)** — `src/lib/expansion.ts`. The `Expansion` type
  (`id`, `name`, `author`, `description`, `version` (integer, monotonic), `createdAt`, `cards: LibraryCard[]`,
  and the content metadata each card needs), plus pure logic: `mergeExpansion(existing, incoming)`
  (the update-in-place / version-compare decision → `'add' | 'update' | 'skip' | 'conflict'`),
  `expansionSummary(exp)` (quick details), and `contentForCreation(enabledExpansions)` → the typed
  lists (ancestries, communities, domains, subclasses, classes) the creation flow consumes.
- **`library-store`** — `src/lib/library-store.ts`. Mirrors `character-store.ts`: persists the library
  (list of expansions) under `Paths.document/library/` as one `.json` per expansion (web `localStorage`
  shim for the verify pipeline). CRUD + `importRkpFile()` / `exportExpansion()` using the existing
  `expo-sharing` / `expo-document-picker` / `expo-file-system` stack. The store is the only place that
  touches the filesystem; all decisions come from the pure `expansion`/`rkp` modules.
- **`library-content`** — typed accessors that adapt `LibraryCard`s into the shapes the existing
  creation code already consumes (a `CatalogCard`-compatible adapter for ancestry/community/domain/
  subclass, and a `ClassData`/`ClassCardDef`-compatible adapter for custom classes), so the creation
  `items` memo can concatenate custom content onto the static lists with minimal new branching.

**Modified modules:**

- **`leveling`** (`src/lib/leveling.ts`) — Bug 2 & 3.
  - `clearsTraitMarks(level)` must return true at **every tier start (2, 5, 8)**, mirroring
    `isTierStart`, not just 5 and 8.
  - Trait-pick dedupe: reject/disable picking a trait already chosen earlier in the **same** level-up
    (across both trait takes) in addition to the persisted `traitMarks`. The apply path must also
    de-duplicate so a malformed plan can't double-`+1` one trait.
  - Bug 3: the owned list (`domainCardIds`) already always appends; the leak is that the UI treats
    `activeDomainCardIds` (capped at 5) as the visible set. Fix the **consumer** so the carousel/Cards
    deck is built from `domainCardIds` (owned), and `activeDomainCardIds` governs only active/equipped
    state. Confirm no level-gated branch drops the owned append.
- **`level-up-panel`** (`src/features/character-sheet/sheet/level-up-panel.tsx`) — Bug 2.
  - The trait chip `disabled` predicate must also disable traits selected in any other current take,
    so the same trait can't be chosen twice across the two trait advancements in one level.
- **character creation** (`src/features/create/create-screen.tsx`, `create-constants.ts`, `create-ui.tsx`) —
  Bug 1 + expansion gate + custom content.
  - Bug 1: replace the edit-only inventory custom flow with the **Mixed-Ancestry button-card pattern**.
    A reserved trailing `'item-add'` card stays as the "Create card" button; activating it appends a new
    custom card to `draft.inventoryCustom` (inserted to the **left** of the button) and opens the editor
    on it. Saved custom cards become **selectable** carousel entries (toggle into the owned set) with a
    separate edit affordance; the button-card's label is always "Create", never "Edit"/"Select".
  - Expansion gate: a pre-step expansion picker shown only when the library has ≥1 expansion; its result
    (enabled expansion ids) feeds the `items` memo via `library-content`.
  - Custom content: the `items` memo concatenates `contentForCreation(enabled)` onto the static catalog
    lists per deck. Custom classes flow through the existing forged class-card + `featurePages` path via
    the `ClassData` adapter.
  - The forge writes the enabled expansion ids (and any per-character custom card definitions needed to
    keep the sheet self-resolving) onto the `CharacterFile`.
- **card archive / gallery** (`src/features/gallery/gallery-screen.tsx`) — Bug 4.
  - Add `ALL_WEAPONS` + `ALL_ARMOR` to the browsable set behind a union item type
    (`CatalogCard | { kind:'weapon', weapon } | { kind:'armor', armor }`). Render equipment via the
    existing `ForgedWeaponCard` / `ForgedArmorCard` (no image assets needed). Extend the filter model
    with `weapon`/`armor` kinds and a **tier (1–4)** dimension reusing the `gear-browser` tier selector
    pattern.
- **`character-file`** (`src/lib/character-file.ts`) — additive, no schema bump if all fields optional.
  - Add optional `enabledExpansionIds?: string[]` and, if needed for self-resolution, embed referenced
    custom card defs (reuse existing `customCards`/`ExperienceDef` shapes where possible). Keep
    `schemaVersion` at 1 (additive/optional fields only).
- **`character-store`** (`src/lib/character-store.ts`) — switch export/import to `.rkp` via the new
  `rkp` envelope; widen the document picker `type` to accept `.rkp`/octet-stream.
- **app config** (`app.json`) — NFC only: add the NFC config plugin + permission/intent-filter **iff**
  NFC ships; otherwise unchanged. (See Out of Scope.)

### Key decisions / contracts

- **One envelope, three kinds.** `.rkp` is JSON `{ format:'rkp', rkpVersion, kind, payload }`. `character`
  payload = existing `CharacterFile`; `card` payload = one `LibraryCard`; `expansion` payload = one
  `Expansion`. Import detects `kind` and routes. (Owner: single cards import to a **sheet**, not the
  library; expansions populate the **library**.)
- **Expansion identity & version.** Each expansion has a stable `id` (uuid, survives renames) and an
  integer `version`. Import compares `id`: unknown → add; known & incoming `version` > mine → update in
  place; incoming ≤ mine → prompt skip/overwrite. Cards reference content by id so existing characters
  keep resolving after an update.
- **Library vs. sheet.** The library store is app-level (not on any `CharacterFile`). Character creation
  *reads* the library (filtered by the session's enabled expansions). A character records
  `enabledExpansionIds` so its sheet can re-resolve custom content later.
- **Custom content adapters.** Custom ancestry/community/domain/subclass present as `CatalogCard`-shaped
  records (with `domain`/`level`/`className`/`subclass`/`tier` as appropriate) so the creation `items`
  memo and the carousel need minimal new code. Custom classes present as a `ClassData`-shaped record so
  `featurePages` and the forged class-card path work unchanged. Mixed-ancestry custom cards carry their
  own `ANCESTRY_EFFECT_TRAIT` value (1|2) and `ANCESTRY_STRIKES`-shaped strike regions.
- **Bug 2 rule (canonical).** Trait advancement: up to 2 distinct traits per applicable level-up; each
  trait at most once **per tier**; marks reset at the **start of every tier (levels 2, 5, 8)**. From a
  prototype of the corrected predicate:
  ```ts
  // tiers start at 2, 5, 8 (T1=1, T2=2–4, T3=5–7, T4=8–10)
  const clearsTraitMarks = (level: number) => level === 2 || level === 5 || level === 8;
  ```
- **Bug 3 rule (canonical).** `domainCardIds` (owned) is the carousel/Cards source of truth and always
  receives the level-up pick. `activeDomainCardIds` (≤5) governs only active/equipped state and never
  gates ownership or visibility.
- **NFC is APK-only and optional.** It requires `react-native-nfc-manager` (not in Expo Go) + a config
  plugin (NFC permission + NDEF intent-filter) regenerated by `expo prebuild`. The file-based `.rkp`
  path is the always-available primary; NFC is a layered shortcut that must never be the sole path.

## Testing Decisions

Good tests assert **external behavior** of the pure modules, not implementation details — same style as
the existing `src/lib/*.test.ts` (`leveling.test.ts`, `favorites.test.ts`, `character-file.test.ts`,
`data-integrity.test.ts`).

- **`rkp.test.ts`** — round-trip each kind (`serializeRkp` → `parseRkp` is identity for character/card/
  expansion); `parseRkp` rejects non-JSON, wrong `format`, unknown `kind`, missing payload.
- **`expansion.test.ts`** — `mergeExpansion`: unknown id → `add`; higher version → `update`; equal/lower
  → `skip`/`conflict`; `contentForCreation` returns the right typed buckets for a mixed expansion;
  `expansionSummary` reports correct card counts/types.
- **`leveling.test.ts`** (extend) — marks **clear at level 2** (new, currently missing); marks clear at 5
  and 8; cannot pick the same trait twice in one level; the level-9/10 trait advancement is completable;
  a domain card chosen at level 3–10 lands in `domainCardIds` regardless of the 5-active cap (extends the
  existing 6th-card test). Update the test at the old `clears at 5 only` assertion to the corrected rule.
- **`character-file.test.ts`** (extend) — `enabledExpansionIds` survives serialize/parse; unknown
  optional fields don't break parsing; schema stays v1.
- Library/creation **UI** is verified manually on device per project convention (animations/interaction).
  No snapshot tests for motion.

## Out of Scope

- **Editing the built-in system catalog.** System cards remain immutable; homebrew lives only in
  expansions.
- **A cloud/account sync or marketplace** for expansions. Sharing is local (file + optional NFC) only.
- **NFC for iOS.** Owner explicitly only wants Android NFC. iOS uses file sharing.
- **NFC verified end-to-end in this release if it risks the APK build.** NFC pulls in a native module
  that cannot run in Expo Go and can complicate the already-fragile native build; it ships only if it
  builds cleanly and is gated behind the file fallback. If it can't be made safe this cycle, it ships as
  a documented follow-up and the file-based `.rkp` path covers all sharing.
- **Retroactively migrating existing per-character `inventoryCustom`/`customCards` into the library.**
  Existing characters keep their embedded custom cards; the library is forward-looking.
- **Deep rules automation for fully custom classes** (e.g. bespoke class-feature automation beyond the
  modifier-engine effects already supported). Custom classes get the same structural support as built-in
  ones (stats, items, hope feature, feature pages, two domains, subclasses, modifier effects); anything
  the engine can't express is authored as descriptive text.

## Further Notes

- **SDK-54 / Expo Go constraint (load-bearing).** The project is pinned to Expo SDK 54 so the owner's
  Expo Go runs it. The `.rkp` file path uses only already-installed Expo modules and works in both Expo
  Go and the APK. NFC's native module breaks Expo Go, so NFC is APK-only; its permission + NDEF
  intent-filter must be added via an `app.json` config plugin (the generated `android/` is gitignored
  and regenerated by `expo prebuild`, so the manifest can't be hand-edited).
- **`.rkp` MIME.** Android has no registered MIME for `.rkp`, so it resolves to
  `application/octet-stream`; the document picker `type` must be widened (`'*/*'` or include
  octet-stream) or `.rkp` files appear greyed out. Parsing is content-based (`JSON.parse` + envelope
  validation), so a renamed file still parses.
- **Things that can go wrong (called out per owner request).**
  - *Level-up + custom content:* a custom class's two domains must resolve to real domain pools (custom
    or built-in) at every level, or the domain step/level-up has nothing to offer — validate a custom
    class declares domains that exist (built-in or in the same expansion).
  - *Custom subclasses across tiers:* built-in subclasses have foundation/specialization/mastery
    (tier 1/2/3) cards; a single-card custom subclass must still satisfy the subclass step and any
    level-up that grants a specialization/mastery card — for v0.10.0 custom subclasses are single-card
    (foundation), and specialization/mastery for custom subclasses is descriptive/manual (flagged).
  - *Mixed ancestry with custom ancestries:* cross-out needs per-card strike regions; a custom ancestry
    without authored regions can't be cleanly crossed out — require regions (or a sensible default) when
    the author enables mixed-ancestry use.
  - *Expansion updates vs. live characters:* changing a card's id on update would orphan it on existing
    sheets — ids are immutable across versions; only contents change.
  - *Removing/disabling an expansion* that a character was built with: the character must still resolve
    its custom cards — hence `enabledExpansionIds` on the file and (where needed) embedding referenced
    defs so the sheet is self-sufficient.
- **Suggested PR slices.**
  1. **PR A — four bug fixes** (inventory button-card, level-up trait reset/dedup, domain-card add at 3+,
     archive weapons/armor). Small, high-value, low-risk; ships first.
  2. **PR B — `.rkp` + library + expansions** (envelope, library store, library screen, card/expansion
     authoring, file share/import + versioning, expansion-gated creation with custom ancestry/community/
     domain/subclass/class content).
  3. **PR C (follow-up) — NFC tap-to-share** (APK-only, behind the file fallback), if it builds cleanly.
