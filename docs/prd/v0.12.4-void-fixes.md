# v0.12.4 — Void banners, ancestry strikethrough & the drop-flash

Owner round-2 feedback on v0.12.3 (3 items), all narrow fixes to the prior round.

## 1. Void class banners actually render (issue 1)
v0.12.3 painted the banner webp through `react-native-svg`'s `<Image href={require(...)}>`, which does **not**
render a bundled raster on Android (New Arch) — the banner showed as a faint sliver. Two changes:
- **Render with `expo-image`** instead of SVG. `voidBanner` still returns an `FC<SvgProps>` (so `ForgedCard`
  and the picker are unchanged), but its body is an `<ExpoImage contentFit="contain" contentPosition="top">`
  sized to the caller's width/height — the reliable raster path the card already uses for `imageUri`.
- **Strip the light watermarked background** from the owner's WIP JPGs → transparent, tight-cropped webp
  (`scripts`-style PIL flood-fill from the borders so interior white glyphs survive). The pennant now sits on
  the deep card exactly like the base SVG banners, top-aligned and width-fit.

## 2. Mixed-ancestry strikethrough in creation (issue 2)
The markdown strike chain was correct and the **sheet** already struck the crossed-out feature (via
`libJobs` → `libraryCardBody(lc, struckIndex)`), but **character creation** rendered structured ancestries
through `libCardItem` with **no** `struckIndex`, so no cross-out showed while picking a mix. Fix:
`libCardItem(lc, struckIndex?)` now forwards a strike index, and the ancestry deck computes it from
`draft.mixedAncestry` (first-picked → strike section 1, second-picked → strike section 0), mirroring the
image-ancestry `ancestryCrossOuts`. The `items` memo already depends on `draft.mixedAncestry`, so the cards
re-strike live as the mix is chosen. (Underlying `parseInline` strike + `libraryCardBody` wrapping are
already unit-tested.)

## 3. The one-frame drop-flash (issue 3)
v0.12.3 deferred the deselect but the flash persisted. Root cause: the drag layout is **identity-correct**
over the reordered deck (pre-written raiseOrder ranks + gap math resolve every card to its new index), so the
real problem is timing — the reordered per-card `index` props reach the UI thread a frame or two **after**
React commits them. When `editGrabbed` flipped to 0 in the post-commit effect, the plain layout painted over
the still-old native indices for one frame → the flash. Fix: `finalizeCommittedDrop` now **holds the drag
layout two `requestAnimationFrame`s** (identity-correct, so seamless) before tearing down — `resetDrag` first,
then the deferred deselect — so the teardown lands only once the new indices are live.
