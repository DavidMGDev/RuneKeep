# v0.34.0 — The moodboard, and four fixes

## Problem Statement

Five things, one of them large.

**A card's description is still cut off on a phone.** The owner typed a 466-character backstory into
the card editor and the preview printed it straight through the bottom of the card, clipping the line
after "murder,". This has been reported across three releases and fixed twice from the wrong theory
each time, so the app looks like it cannot lay out its own text.

**The timeline crawls.** At 98 recorded changes, scrolling the Timeline tab stutters.

**The Homebrew filter lies.** It offers to narrow a category to homebrew when that category has no
homebrew in it, and a Homebrew selection made in Ancestry stays lit after switching to Community,
where it shows an empty list.

**The portrait feels dead.** A tap gives feedback almost half a second later, and a hold gives
nothing at all for the first half second, so both read as the app ignoring you.

**A character has nowhere to keep what it looks like.** Players collect reference art, faces, places
and scraps for a character, and RuneKeep has one portrait slot. Everything else lives in a photo
album that has nothing to do with the character and never travels with it.

## Solution

**The card text is sized against the device's own font scale.** The renderer was multiplying every
size on the card by the phone's accessibility text scale AFTER the app had chosen a size to fit the
box. Measured from the owner's screenshot at three independent points on the card, all agreeing on
about 1.15. A forged card is a fixed-size printed artifact whose type is already auto-fitted, so it
opts out of that scaling, and both platforms then draw what the arithmetic asked for.

**The timeline pages in as you scroll**, twenty entries at a time, and stops re-diffing every
snapshot on every render.

**The Homebrew chip appears only where there is homebrew**, and a selection that no longer applies
clears itself on the way into the new category.

**The portrait answers instantly** on touch rather than on release, and its hold feedback starts
immediately.

**Double-tapping the portrait opens the moodboard**: a flat, borderless canvas that belongs to the
character, where images can be placed, dragged, pinched, rotated and arranged, that is locked by
default, and that travels inside the character file like everything else.

## Implementation Decisions

### Card text and the device font scale

- Measured from the owner's screenshot: the card renders at 648 image pixels for its 230 design-px
  width. Working back from three separate strings (the body's first line, the footer's copyright, the
  title) gives an implied font size of 9.67 against a declared 8.5, 7.13 against 6.3, and 20.16
  against 17. Three independent points, all about **1.13 to 1.19**, which is Android's second text-size
  step. The fitter chose correctly and the renderer scaled everything afterwards.
- Forged cards opt out of OS font scaling. The card is a fixed-size printed artifact and the app
  already chooses a size to fit its geometry; a second, invisible multiplier applied after that
  calculation can only overflow it. This is the same class of decision as switching off Android's
  `includeFontPadding` in v0.33.0.
- Accessibility is not being dropped: the card's own auto-fit is the sizing mechanism, and the
  fullscreen card view is how a card is read larger.
- No change to `lib/fit-text`. It has now been verified correct against real font metrics twice.

### Timeline

- The timeline pages: an initial page of entries, extended as the scroll approaches the bottom.
  `OverlayShell` gains an end-reached callback so the page grows from the shell that owns the scroll
  view, rather than each panel growing its own.
- The per-row "which cards moved" diff currently finds its previous snapshot with a linear search per
  row, which is quadratic over the whole timeline. The previous-snapshot lookup becomes a single map
  built once per history.
- Pagination is preferred over virtualization: rows are variable height and the panel is a plain
  scroll view, and a windowing list inside a chamfered overlay has bitten this codebase before.

### The Homebrew filter

- A pure predicate answers "does this category have any homebrew", given the loaded expansion cards.
  The chip renders only when it is true.
- When the category changes and the current source filter is no longer offered, the filter resets to
  showing everything. When it is still offered, the selection is kept.
- Applies to both the sheet's gear browser and the card archive, which already share the same
  category-to-content mapping.

### The portrait

- Tap feedback fires on touch-down rather than on gesture end, so it cannot be delayed by the
  double-tap window that this release introduces.
- Hold feedback starts effectively immediately and completes sooner.
- A double tap is added, resolved exclusively ahead of the single tap so the two never both fire.

### The moodboard

**Where it lives.** A character-scoped screen, opened from the sheet, rendered inside the same design
stage the sheet uses so a tablet gets it through the existing phone frame with no special case. The
sheet unmounts while it is open.

**Model.** The character file gains an ordered list of moodboard items. Array order IS z-order, last
on top, so every layer operation is an array move and there is no separate z field to keep in sync.
Each item carries an id, an image reference, a centre position in canvas units, a scale, a rotation in
degrees, and the image's natural aspect ratio so layout is stable before the image decodes.

The image field is named to match the other authored-card collections, so three existing mechanisms
cover it for free: export embedding, history snapshot stripping, and the import-side dropping of dead
browser blob references.

**Two deep modules, both pure and both tested.**

- A moodboard model module: add, remove, duplicate, centre, bring to front, send to back, one layer
  up, one layer down, and a clamp that keeps an item's centre inside the canvas. No React, no
  persistence, no image handling. This is where every correctness question about ordering and
  bounds lives.
- A snapping module with hysteresis. This is the subtle one and the reason it is separated: a snap
  that engages and releases at the same threshold chatters, and a snap with no escape traps the user.
  It takes a raw continuous value, the set of targets, an enter threshold and a larger exit threshold,
  plus whether it is currently snapped, and returns the value to display and whether it is snapped.
  Used for both rotation (right angles) and position (canvas centre lines). From the prototype, the
  decision it encodes:

  ```
  engaged && |raw - target| < exit   -> stay snapped to target
  !engaged && |raw - target| < enter -> snap to target, fire a haptic once
  otherwise                          -> show raw
  ```

  with `enter < exit`, which is what makes it stick the way a photo app does.

**Gestures.** Pan, pinch and rotation composed simultaneously on each item, so two fingers do all
three at once. All driven by shared values; nothing is written to state or disk during a gesture, only
on its end. Gesture translations are divided by the stage scale on web, where gesture-handler reports
CSS pixels because the magnifying transform is on an ancestor. That convention has been got wrong
twice in this codebase and is the first thing to check if the web build misbehaves.

**Controls.** Top right, right to left: exit, lock, layer list. Bottom centre: add, shown only when
unlocked and hidden while an item is being moved.

**Locking.** The board opens locked every time, regardless of how it was left, because the alternative
is arriving on a live canvas and nudging something. Unlocking requires a one-second hold with a
progress indicator. Locking again is a single tap. The lock state is not persisted.

**The radial menu.** Double-tapping an item opens a tap-driven radial wheel with delete, duplicate,
bring to front, send to back, and centre. It is the same visual language as the gear-edit wheel but
without the finger tracking, since it is opened by a tap rather than held. It is positioned at the
item and clamped to stay fully on screen.

**Deletion.** The pre-v0.33.1 token departure: gravity, drift, spin and fade. Explicitly without the
throw momentum added in v0.33.0, which is a dice affordance and not wanted here.

**Transitions.** Entering and leaving cross-fade. The background arrives first, then the controls,
then the images as they decode. Nothing appears at full opacity in a single frame.

**Performance.** One image view per item and never a LOD pair, which is the v0.33.1 lesson. Items are
memoized. The moodboard field is added to the set of cosmetic fields that must not invalidate the
sheet's deck memos, so arranging images cannot rebuild the carousel.

**Onboarding.** The sheet tour gains a page for it.

**Libraries.** None added. Reanimated and gesture-handler are already wired and are what a third-party
canvas would be built on; adding a dependency here would be more code, not less.

### The duplicated ancestries, and the flicker they were causing (v0.34.0, added mid-release)

The six Hope and Fear ancestries are authored as structured library cards on the expansion record, and
v0.12.3 removed their rows from the generated catalog BY HAND. Regenerating the catalog in v0.32.0 put
them straight back, so the creator listed each of them twice: once from the catalog and once from the
expansion.

That is also, in all likelihood, the flicker. Two cards with one id means two slots with one React key
and two image views with one recycling key, at the end of the deck, which is exactly where it was
reported and nowhere else. The two earlier attempts at it (v0.33.0's move to an image path, v0.33.1's
removal of the duplicate image layer) were both real improvements aimed at the wrong thing.

The exclusion moves into the generator, where the beta pack split already lives, for the same reason:
a hand edit to a generated file survives exactly until the next generation. A test fails if a
structured ancestry ever reappears as a catalog row, and a second one fails on any duplicate id at all.

### The trash

Three separate faults, all reported together.

- Deleting an authored card BOTH splices it out of its collection and tombstones its id. Restoring
  only undid the splice, so the card came back to a file that went on hiding it. That is why restoring
  the default note produced nothing.
- A catalog card is never spliced, only tombstoned, and the trash only looked at authored collections.
  So a deleted armor was not in the trash at all. Tombstoned cards are listed now; they carry no card
  object, because nothing was removed, and restoring one lifts the tombstone.
- Deleting a card drops its category, and restoring did not put one back, so a restored card fell to
  whatever its kind defaults to. Restoring asks, through the same destination prompt every other card
  in the app passes through.

Titles for system cards are resolved by the SCREEN, not the history model, which has no catalog to
look one up in.

### The category list

- A switch that cannot move says why, through the sheet's existing notice channel: empty is the common
  case, and last-one-standing was silent for the same reason.
- The rows press. Tapping one used to move you with no acknowledgement at all.
- The lit colour moves off the heraldic red, which the app uses for damage and for deletion, onto a
  muted bronze. The CURRENT category takes the bright gold and a spine down its left edge, so the two
  states are told apart by hue rather than by a word in small print.

## Testing Decisions

A good test here states an external behaviour and would survive a rewrite of how it is achieved. It
does not assert on component internals, shared values, or the order in which effects run.

- **The moodboard model module** gets the fullest suite: adding puts an item on top; removing takes
  the right one; duplicating places a copy above the original and offset from it so it is visibly a
  copy; layer up on the topmost item is a no-op rather than an error; bring to front and send to back
  are idempotent; centring puts an item at the canvas centre without changing its scale or rotation;
  the clamp keeps a centre inside the canvas from every direction; and every operation returns a new
  list rather than mutating its input, which is what the save path relies on.
- **The snapping module** gets the hysteresis pinned explicitly: it snaps on approach, it stays
  snapped through the dead band, it releases only past the wider exit threshold, it reports the
  transition exactly once so a haptic cannot repeat, and it handles wrap-around at 360 degrees.
- **The homebrew predicate** is tested against a category with homebrew, one without, and the
  switch-between case that motivated it.
- **The trash** is tested on the three faults directly: an authored card comes back with its
  tombstone lifted, a tombstoned system card is listed and restorable, and a restored card lands
  in the deck that was chosen.
- **The catalog** is tested for duplicate ids, and for any structured ancestry reappearing as a
  catalog row, so a regeneration cannot quietly undo the fix.
- Prior art for all three: `src/lib/*.test.ts`, which are plain assertion suites over pure functions
  with no framework beyond Jest. `character-history.test.ts` is the closest model for "a pure module
  with a lot of small behaviours".
- Not unit-tested, deliberately: the gesture composition, the transitions, and the radial menu. They
  are animation and touch, which this project verifies on a device by convention. The font-scale fix
  is a render prop with nothing to assert about; its evidence is the measurement in this document.

## Out of Scope

- Drawing, text, stickers or filters on the moodboard. Images only.
- A scrollable or zoomable canvas. The canvas is fixed to the screen, which is what makes "nothing can
  be lost" tractable.
- Sharing a moodboard on its own, separately from its character.
- Multiple moodboards per character.
- Reordering by dragging within the layer list.
- Any change to `lib/fit-text`, which has now been verified correct twice.
- Virtualizing the timeline.

## Further Notes

The card-text fix is the third attempt at this report and the first with a measurement behind it. The
two earlier theories (Android's line metrics differing, and glyphs being wider than assumed) were both
disproved by reading the font file; the remaining native-only terms were `includeFontPadding`, fixed
in v0.33.0, and the OS font scale, fixed here. If a description still overflows after this, the next
step is a line count measured on the device, not a fourth theory.

The moodboard touches three mechanisms added in the last two releases, and gets them for free by
naming its image field the way the other collections name theirs: export embedding, history snapshot
stripping, and blob dropping on import. It also has to join the cosmetic-fields set added in v0.33.1,
or arranging images will rebuild the entire card carousel on every drag.
