# v0.42.3 — Feature cards, and the authoring overhaul

## Problem Statement

The homebrew authoring surface works but it is not usable, and one shipping mistake broke the update
link for everyone already on the app.

From the owner's chair:

- **The update link is dead.** v0.42.2 was published by hand and only the versioned APK was uploaded,
  so `/releases/latest/download/RuneKeep-android.apk` (what the website's Android button points at)
  404s. The build script has always uploaded both; the manual path skipped it, and nothing stopped it.
- **Functional elements are offered on every card type**, so a Weapon and an Ancestry both ask whether
  they would like a counter. They are the whole point of exactly one kind of card, and that kind is
  not even called that.
- **You cannot see what you are making.** A functional element is previewed inside its own
  configuration panel, on a grey form background, at a size and shape it will never have on the card.
  The card preview at the top of the editor shows the card without it.
- **The forms ask for typed text where the app already knows the answer.** A domain card's level is a
  free text box that must be 1 to 10. Starting Evasion and starting Hit Points are text boxes. A
  cycling button's options are one blob of lines separated by newlines. Every one of these is a place
  the app could offer a control that cannot be wrong, and instead offers a keyboard.
- **The functional element form is upside down.** The subtitle is the first thing asked for, before
  the author has decided what the element even is. "Where it sits" offers above-the-text or
  below-the-text, which is not a real question once elements live in the section list. "Line above"
  and "line below" solved a problem the author did not have: they can already write text.
- **The section editor cannot express what a feature card is.** Sections and functional elements are
  two separate lists, so an element cannot sit between two paragraphs. There is no text alignment. The
  Bold and Italic buttons need a selection and close the keyboard. The bullet button is a dot and the
  italic button is a capital I; neither reads as what it does.
- **A level advancement is one effect for every tier**, so a class whose Tier 2 option differs from
  its Tier 4 option cannot be written at all.
- **A feature card can be replaced by a whole card image**, which silently discards the elements that
  are the only reason it exists.
- **Domain and Domain Card have no plaque of their own** and fall through to the generic parchment,
  breaking a rule every other card type keeps. And a domain card cannot be given the type the printed
  ones carry (Ability, Spell, Grimoire), so homebrew domain cards never look like the real thing.
- **A counter's floor and ceiling are two text boxes where 0 means "none"**, which nobody would guess
  and which leaves two fields on screen doing nothing most of the time.
- **A functional element cannot be used as a variable.** A Combo Die is a number on a card and the
  dice tray cannot roll with it.
- **Authoring hijacks the app.** Opening an expansion offers to turn DM mode on, which DM playtesters
  disliked: they wanted the colours, not the mode, and not two pop-ups on the way in.
- **Campaign settings are checkboxes.** The owner asked for the Characterize experience: walk the real
  character creator and turn cards off from inside it. What shipped is a list of labels.
- **The expansion screen is a list.** Cards the author drew are shown as rows with a colour diamond.
  Edit info / Campaign / Share are three cramped ghost buttons over a wall of rows, and "Campaign"
  leads through two pop-ups before it does anything.
- **Class creation still has the wrong shape.** There is no moment where the author says whether they
  are starting a class or adding a page to one that exists. The Hope feature is a special field in the
  form when it should be a section like any other. Domains print lower-cased. Starting items are three
  chip clouds with a search box, when the app already has a card-picking interface built for exactly
  this.
- **"What are you making?" has an "Anything else" section** that means nothing, and the Feature card
  is not where an author would look for it.
- **An expansion is one tap and one confirm from being gone**, while a DM campaign takes a hold, a
  menu, and two escalating confirmations. An expansion is more work than a campaign, not less.

## Solution

One release that finishes the authoring surface and makes the release script the only way to publish.

**Feature cards.** The card type formerly called a functional card is a **Feature card**, it lives in
the Class section of "What are you making?", it replaces the plain Card entry there, and it is the
only card type that offers functional elements. Its section describes what they are for: advanced
tracking, level advancements, and anything a class needs a player to hold a number for.

**One list, not two.** A card's body is an ordered list of **sections**, and a section is either text
or a functional element. `+ Add Section` and `+ Add Function` both append to the same list, so an
element can sit anywhere, and reorder buttons move either kind. Placement chips are gone; the order is
the placement.

**The preview is the preview.** The card at the top of the editor renders the real card, elements and
all, exactly as the player will see it in their arsenal. Nothing is previewed anywhere else.

**Controls, never typed text, wherever the app knows the answer.** A sweep of every authoring form:
levels, evasion, hit points, tiers and counts become counters with real bounds; option lists become
add/remove/reorder entry lists; anything from a fixed set becomes a selector.

**Elements are configured then customised, in that order.** Kind first, then its rules, then how it
looks on the card (full width or hugging its content, small/medium/large), and every one of those
choices is visible on the preview as it is made. A title above the element is standard and centred,
with one control to remove it.

**Elements are variables.** A counter or a numeric cycling button becomes a named variable available
to dice presets and modifier formulas. It can be read; it can never be written to by a modifier.

**Campaign settings ARE the character creator.** The DM opens the creator in campaign mode and walks
the same carousels a player walks. Tapping a card disables it. Turning a step off is the same rail.
Everything the model already does (union across packs, only-what-is-off stored, steps that empty
themselves out) is kept exactly; only the surface changes.

**The expansion screen is a gallery.** Rendered cards, as they look in the game, in a grid paged to
what fits the screen. Tap to edit, hold to select, and a selection can be shared, moved or deleted.
The header is re-laid out with real labels.

**Deleting an expansion is as hard as deleting a campaign.** Hold, menu, then two escalating
confirmations.

## Implementation Decisions

### Release

- `apk-build/build-apk.ps1` gains a `-PublishOnly` switch that skips gradle and runs the upload step
  against the APK already on disk. This exists so the foreground-build-then-publish workflow (which
  is what has to be used, because a long background build gets killed) never goes through a hand
  written `gh release create` again.
- The upload step asserts BOTH asset files exist before calling `gh` and fails loudly if either is
  missing. The stable-name asset (`RuneKeep-android.apk`) is what
  `/releases/latest/download/RuneKeep-android.apk` resolves to, and it is not optional.
- v0.42.2's release is repaired by uploading the stable-name asset to it.

### The body becomes one ordered list

- `CardSection` gains `functionId?: string`. A section carrying one IS that functional element; its
  `body` is unused. This is additive: every existing renderer that walks `sections` keeps working, and
  a card written before this release has no function sections.
- `CardFunction` loses `placement`, `before` and `after`. Position is the section's position. A card
  saved with the old fields is migrated on READ (a tolerant read, the v0.41.4 rule): functions with
  `placement: 'above'` become sections before the text, `'below'` after it, in their existing order.
  `before`/`after` text becomes ordinary text sections around it, so no authored words are lost.
- New module **`lib/card-blocks.ts`**: the ordered view and the edits on it.
  `blocksOf(sections, functions)` → `{ section, fn? }[]`; `withFunctionSection`, `withoutFunction`,
  `moveBlock`, and `migrateLegacyPlacement(card)`. Pure, no rendering.

### The functional element

- `CardFunction` gains:
  - `title: string` and `titleHidden?: boolean`. Every element has a title (it is the variable's
    name); one control removes it from the card. The title renders centred, above the control, in
    smaller type.
  - `width: 'full' | 'hug'` (default `hug`).
  - `size: 'small' | 'medium' | 'large'` (default `medium`).
  - `label` (the old subtitle) is REMOVED.
- The counter's floor and ceiling are gated by explicit switches in the form; the model keeps
  `min`/`max` as `number | undefined`, where undefined means no bound, so the model does not grow two
  redundant booleans.
- A cycle's `options` are edited as a list of entries with add, remove and reorder, never as a
  newline-separated blob.

### Feature cards

- `LibraryContentType` gains `'feature'`. It is the only type whose editor offers `+ Add Function`,
  and the only type where `functions` may be non-empty. `'generic'` remains for plain cards but is no
  longer offered as its own entry in the class group.
- The whole-card-image control is not rendered for a feature card.
- `TYPE_GROUPS` in the type chooser: the class group becomes class / subclass / feature, the
  "Anything else" group is removed, and the class group's hint says what feature cards are for.

### Level advancements per tier

- `CardAdvance.effect` stays as the default. It gains
  `byTier?: Partial<Record<2 | 3 | 4, { label?: string; effect?: AdvanceEffect }>>`. Absent means the
  default applies at every tier it is offered at, which is the common case and stays one line in the
  form. `advanceFor(advance, tier)` resolves the pair.

### Elements as variables

- `EffectFormula.variable` gains `'function'`, paired with a new `functionKey` field of the form
  `cardId|functionId`. Resolution reads `SheetContext.functions`, exactly as `'input'` reads
  `ctx.inputs`. Read-only by construction: no `CardEffect.target` can name a function, so a modifier
  can use one and can never write one.
- The variable pickers (modifier formula editor, dice presets) list a character's numeric elements by
  their `title`, and list nothing for text elements or cycles whose options are not numbers.
- New helper in **`lib/card-advances.ts`** or a small **`lib/function-vars.ts`**:
  `numericFunctions(cards, states)` → `{ key, title, value }[]`. One place decides what counts as
  numeric, so the two pickers and the resolver cannot disagree.

### Campaign settings in the creator

- The creator gains a campaign mode, entered with a route param naming the expansion being edited
  (`/create?campaign=<expansionId>`). In that mode:
  - Tapping a card toggles its key in that expansion's `CampaignSettings.disabled` instead of
    selecting it. The carousel's existing "greyed" treatment (already built for the Inherit step) is
    reused for a disabled card, so nothing new has to be drawn.
  - The rail lets a whole step be switched off.
  - Forging is replaced by Done, which saves the expansion.
  - `syncSteps` still runs, so a step whose last card was disabled turns itself off.
- `lib/campaign-settings.ts` is unchanged apart from anything the new surface needs. The union, the
  only-what-is-off storage and the player-facing note all stay.
- The checkbox form is deleted.

### The expansion screen

- The card list becomes a **gallery of rendered cards**, using the same forged card components the
  rest of the app uses, in a grid, paged. New module **`lib/expansion-gallery.ts`**: how many fit,
  which cards are on a page, and the selection rules (tap = edit, hold = enter selection, tap in
  selection = toggle). `lib/gallery-select.ts` is the prior art and is reused where its rules fit.
- Header: a single row of clearly labelled actions, and the destructive one is not in it.
- Deleting an expansion follows the campaign pattern exactly: hold a row (or a Delete entry reached
  from a menu), then a first confirmation naming what goes, then a shouting second one.

### The class card

- `CustomClassSpec` gains `role: 'base' | 'page'`. `base` is the class's summary page and the thing
  other cards point at; `page` names an existing class (custom or built-in) and is another page of it.
  The chooser is the first thing in the form.
- `hopeFeature` is removed from the form. Existing specs keep the field (tolerant read) and it is
  surfaced once as a section the author can keep or delete.
- Starting items are picked through `GearBrowser` in a select mode, which already renders real cards,
  already has category tabs, and already surfaces expansion records.
- Domain names are capitalised for display everywhere. The stored keys are unchanged, so nothing
  migrates; a display helper does the work.

### Plaques

- `KIND_THEMES` gains `domain card`, `feature`, `grimoire` and anything else the domain-card type list
  offers that is not already there. Domain card types offered: Ability, Spell, Grimoire.

### Form controls

- New **`components/form-controls.tsx`**: `CounterField` (bounded, hold to repeat), `EntryList` (add,
  edit, remove, reorder), `SwitchRow` (the "Counts down only" shape), `SelectRow`. Every authoring
  form is swept onto these. This is where issue 4's "no weak text edits" is enforced once rather than
  argued case by case.

### Markdown toolbar

- New module **`lib/markdown-marks.ts`**: `applyMark(text, selection, mark, pressCount)` returning the
  new text and the next press state. The cycle is word → whole section → cleared, and the press count
  resets whenever the text changes for any other reason. Keyboard focus is preserved by never
  re-mounting the input and never calling blur.
- `CardSection` gains `align?: 'left' | 'center' | 'right' | 'justify'`, rendered by the forged card.

## Testing Decisions

A good test here asserts external behaviour: what a pure function returns for an input a user could
actually produce. It does not assert that a component rendered a particular view, and it does not
reach into a module's internals. The project's prior art is `src/lib/*.test.ts` — `card-advances`,
`campaign-settings`, `expansion-sort` and `card-move` from v0.42.2 are the closest models, and
`data-integrity.test.ts` is the model for asserting a data table stays coherent.

Tested:

- **`lib/card-blocks.ts`** — the ordered view, insertion, removal, reorder, and the legacy migration:
  an old card with an above-placed function and a "line below" comes back as the same content in the
  same order, and nothing authored is dropped.
- **`lib/markdown-marks.ts`** — the press cycle (word, section, cleared), that typing resets it, that
  a cursor in the middle of a word marks the whole word, and that marking is reversible.
- **`lib/card-functions.ts`** — the new title/width/size defaults, and that a counter with no bound
  behaves as before.
- **`lib/card-advances.ts`** — per-tier resolution: a tier with no override gets the default, a tier
  with one gets its own, and the existing per-tier limits are unaffected.
- **`lib/modifiers.ts`** — a `function` variable resolves from context, resolves to zero when the
  card is gone, and cannot be a target.
- **function variable listing** — a counter is offered, a text field is not, a cycle of words is not,
  a cycle of numbers is.
- **`lib/expansion-gallery.ts`** — paging, and the selection state machine.
- **`lib/custom-class.ts`** — the base/page split, and that a page card validates against the class it
  names.
- **`lib/campaign-settings.ts`** — existing tests must all still pass unchanged, since the model is not
  changing. That is the regression guard for issue 13.

Not tested automatically, verified by the owner on device (the project's standing rule for motion and
layout): every screen's layout, the live preview's fidelity, the creator's campaign mode, and the
gallery's feel.

## Out of Scope

- Any change to the `.rune` wire format beyond additive fields. Old packs must still import, and packs
  written by v0.42.3 must still open on v0.42.2 with their text intact.
- Rewriting the forged card renderer's typography or geometry. Elements are drawn inside the existing
  card body.
- Any DM screen other than removing the expansion's DM-mode toggle.
- Custom domain card ART. The domain card TYPE gets a plaque; it does not get a painted background.
- Changing how the character sheet stores function state. `cardFunctions` is unchanged.
- Adding a way for a modifier to WRITE a functional element's value. Explicitly refused by the owner.

## Further Notes

- The v0.42.2 release must be repaired before anything else, because the broken link is live now.
- Two rules from earlier releases apply directly to this work and are easy to break again: a card the
  player can press must render LIVE and never as a forged bitmap, and any change to a forged card's
  appearance requires the forge signature to be regenerated.
- The functional-element title is doing double duty as the variable name. That is deliberate: a
  separate "variable name" field would be a fifth thing to fill in, and an element the author did not
  bother to name is an element nobody wants in a formula list.
- No user-visible string in any of this may contain an em dash.
